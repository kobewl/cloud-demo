01单体架构 vs 微服务架构

Java 类比：单体 = 一个巨型类（God Class）；微服务 = 按职责拆成多个类，类与类之间通过"接口"（HTTP/RPC）通信。

单体 Monolith
  • 整个系统 = 一个进程、一个 jar、一个数据库
  • 内部方法调用，不经过网络，性能好、开发简单
  • 代码膨胀后：编译/启动慢，改一行要全量回归测试
  • 无法按模块独立扩容（只能整体复制）
  • 单点故障：一个模块内存溢出，拖垮全部
  • 技术栈被锁定，无法局部替换旧模块
微服务 Microservices
  • 按业务职责拆成多个独立进程，各自独立部署
  • 服务间通过 HTTP/RPC 调用（你项目里是 OpenFeign）
  • 每个服务独立数据库，独立伸缩，独立出故障
  • 改一个服务只重新部署它自己，其他不受影响
  • 不同服务可以用不同技术栈、不同语言
  • 代价：把"方法调用"变成了"网络调用"，引入一堆新问题（见 03）

04拆了之后的新问题 → 组件全家桶

    
拆分解决了单体的痛点，但把"方法调用"变成"网络调用"后，产生了下面 8 个新问题。微服务技术栈几乎全部是围绕这些问题发明的。

    

      
        
新问题解决方案（组件）Java 类比你的进度

      
      
        

          服务地址会变，怎么找？
          服务注册发现 · Nacos
          动态花名册 / 电话簿：报名字（服务名）就能查到地址
          ✅ 已实现 P2
        

        

          配置散落在每个服务里，怎么统一管理？
          配置中心 · Nacos Config
          一个集中式的 application.yml 仓库，改一处全广播
          ✅ 已实现 P5
        

        

          外部请求从哪个口进？鉴权/路由统一在哪做？
          API 网关 · Spring Cloud Gateway
          DispatcherServlet 前面的总 Filter：先统一处理，再转发给具体 Controller
          🔄 P6 规划中
        

        

          一个服务部署了 3 个实例，调用时选哪个？
          负载均衡 · Spring Cloud LoadBalancer
          轮询派活的调度员（Nginx 的"平均分配"思想）
          ✅ Feign 内置
        

        

          下游服务挂了/响应慢，如何不拖垮自己？
          熔断/限流/降级 · Sentinel
          断路器 + 水坝：快失败 + 防止洪水冲垮系统
          🔄 P7 规划中
        

        

          一次请求跨 3 个服务，出问题怎么排障？
          链路追踪 · Micrometer Tracing / SkyWalking
          贯穿整条调用链的 traceId：像快递单号，全程可查
          ⏳ P8
        

        

          扣库存 + 减余额分属两个服务，怎么保证都成功/都失败？
          分布式事务 · Seata
          跨服务的事务管理器（AT/TCC/SAGA 模式）
          ⏳ P8
        

        

          高并发下单，数据库扛不住怎么办？
          消息队列 · RocketMQ
          邮局：投递完就完事，对方有空再取，实现削峰解耦
          规划中
        

        

          服务多了，部署/伸缩/编排怎么办？
          容器化 · Docker + K8s
          集装箱（镜像）+ 港口调度（K8s）
          ✅ Docker 已用
        

      
    

  


  
  

    
05微服务的代价（先泼冷水）

    
微服务不是银弹。小团队 + 小项目用单体更划算；下面这些是它必然引入的成本。

    

      
网络不可靠
延迟、超时、重试、乱序。本地方法调用不会超时，远程调用会——所以要熔断、超时、重试。

      
分布式数据一致性
一个业务跨多库，本地事务失效，需要最终一致性方案（本地消息表 / Seata / MQ）。

      
排障困难
问题可能藏在 3 个服务里，需要链路追踪 + 统一日志 + 监控告警。

      
测试更复杂
端到端测试要同时起多个服务；Mock 成本高。

      
运维成本翻倍
要管注册中心、配置中心、网关、监控，还要容器化编排。

      
团队组织约束
康威定律：服务边界最好贴合团队边界，拆错边界维护成本巨大。
