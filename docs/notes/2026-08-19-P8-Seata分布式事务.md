## 一、你要学什么

1. **分布式事务**为什么需要：跨服务、跨数据库的操作没有"全局原子性"，本地事务管不到
2. Seata 是什么：Java 微服务领域做分布式事务的事实标准（相当于事务界的 Nacos）
3. 三个角色 TC / TM / RM 各干什么（架构维度，永远存在）
4. 四种模式 AT / TCC / SAGA / XA 的区别（实现维度，选其一）
5. **AT 模式**的原理：undo_log 账本 + 进程外的 TC 自动回滚
6. 为什么手动补偿永远做不到 Seata 的可靠性（崩溃场景）

## 二、生活类比

- **Seata** ≈ 一家餐厅的**后厨管理**：把所有灶台（数据库）的"上菜"变成一场统一指挥
- **TC（事务协调者）** ≈ 后厨**前台调度员**：只拿对讲机不碰菜，记录"每桌点了什么、谁负责哪道菜、做到哪一步"，谁掉线立刻发现
- **TM（事务管理器）** ≈ **点单经理**：只喊三句话——"开一桌！" / "这桌齐了，上菜！" / "这桌毁了，重做！"
- **RM（资源管理器）** ≈ 每个**厨师**：管自己灶台（本地数据库事务），做菜前给食材**拍原样照片**（undo_log），TC 说重做就按照片复原
- **AT 模式** ≈ **自动炒菜机 + 拍照留档**：机器自己记录"改之前长什么样"，出问题自动按照片逆向恢复
- **undo_log 表** ≈ 后厨的**操作台账**：每个厨师改了什么、改之前是什么样，全记在册

**Java 类比**：
- `@GlobalTransactional` ≈ 给方法包一个 `@Transactional` 的"全局放大版"：TM 开事务 → 执行业务 → 提交/回滚
- Seata 数据源代理 ≈ 给 `DataSource` 套一层 `Proxy`：业务代码里的 `connection.commit()` 被"截胡"，
  先向 TC 上报再提交（类似 Spring AOP 拦截）
- XID 传递 ≈ 类似 `traceId` 贯穿整个调用链：靠 Feign 拦截器自动塞进 HTTP header

## 三、为什么需要 Seata？（手动补偿的三大缺陷）

订单服务之前的下单流程：Feign 查商品 → Feign 扣库存 → 本地落订单，落单失败就手动 `addStock` 回补。
这是"人肉版补偿"，但有三个补不上的洞：

| 缺陷 | 场景 | 手动补偿的下场 |
|------|------|--------------|
| ① 崩溃无人补偿 | 扣库存成功、落单前进程被 `kill -9` | 补偿代码在尸体里，库存永远少了 |
| ② 补偿本身会失败 | 落单失败调 `addStock`，库存服务恰好也挂了 | 补偿抛异常，库存还是少了 |
| ③ 补偿时机误判 | 落单其实成功，只是响应超时，业务误判失败去回补 | 库存多加了，订单也多了一张 |

**根因**：补偿逻辑和业务逻辑住在**同一个进程**里。出事的那个人，就是需要救人的那个人。

**Seata 的解法**：把"协调与补偿"从业务进程里搬出去，变成**独立的 TC 服务 + 数据库里的 undo_log 账本**。
补偿指令来自进程外的 TC，回滚数据躺在数据库里——进程死活不影响恢复。

## 四、三个角色（架构维度：谁参与）

| 角色 | 全称 | 部署位置 | 职责 |
|------|------|---------|------|
| **TC** | Transaction Coordinator（事务协调者） | **独立服务**（seata-server） | 记录全局事务状态、每个分支的进度；心跳发现掉线；指挥提交/回滚 |
| **TM** | Transaction Manager（事务管理器） | **业务服务内嵌**（下单方法） | 发起全局事务；决定提交还是回滚（三句话） |
| **RM** | Resource Manager（资源管理器） | **业务服务内嵌**（每个数据库） | 执行本地事务；写 undo_log；向 TC 上报分支结果 |

一句话：**TM 决策，TC 调度，RM 干活。**

---

## 五、四种模式（实现维度：回滚怎么做）

| 模式 | 一句话 | 适用场景 |
|------|--------|---------|
| **AT** | 自动：靠 undo_log 照片逆向补偿 | **默认首选**，侵入最小（只加注解） |
| **TCC** | 手动：业务自己写 Try / Confirm / Cancel | 需要精细控制、AT 不适用时 |
| **SAGA** | 编排：正向操作 + 反向操作依次执行 | 长流程、跨年事务 |
| **XA** | 数据库原生两阶段提交 | 性能差、锁久，一般不用 |

本项目选 **AT**：改动最小，学习价值最高（又能看到一张新表）。

> ⚠️ 概念澄清：TC 是"谁参与"的架构维度，**任何模式都需要 TC**；
> AT 是"回滚怎么做"的实现维度。两者不是一回事，别混。

## 六、AT 模式全流程（下单场景）

### 前置条件（每个参与服务）
1. 数据库建 `undo_log` 表（回滚账本）
2. 数据源换成 Seata 代理（`DataSourceProxy` 包一层，业务代码无感知）

### 正常流程
```
① TM（下单方法）→ TC：开全局事务，TC 返回 XID（全局事务编号）
② XID 自动塞进 Feign 请求头，传到库存服务
③ RM（库存服务）UPDATE quantity=8→6
    代理数据源：改前拍照(before=8) → 执行SQL → 改后拍照(after=6)
    → 照片存 undo_log → 本地事务提交 → 向 TC 报到"分支1 完成"
④ RM（订单服务）INSERT 订单 → 同样拍照存 undo_log → 提交 → 报到
⑤ TM → TC：全部成功，提交！TC 逐个通知 RM 清理 undo_log
```

### 失败流程
```
⑤' TM → TC：回滚！
    TC 逐个通知 RM：读 undo_log 照片 → 生成反向 SQL（UPDATE quantity=8）→ 恢复原样
```

### 关键点
- 每个服务里的**本地事务照常用自己的 `@Transactional`**——Seata 管的是"本地事务之上那一层"
- 提交时数据已真实落库，回滚靠 undo_log"照片"逆向恢复——本质还是补偿，但补偿者变成了**可靠的 TC + 数据库账本**
- **崩溃场景**：某 RM 扣完库存后整个服务崩了，TC 通过**心跳超时**发现掉线 → 主动对所有已注册分支回滚。
  补偿指令来自进程**外**，所以进程死活不影响恢复——**这是手动补偿永远做不到的**

## 七、源码深挖

### 1. undo_log 表（官方标准建表 SQL，每个参与库都要建）

```sql
CREATE TABLE IF NOT EXISTS `undo_log`
(
    `branch_id`     BIGINT       NOT NULL COMMENT '分支事务ID',
    `xid`           VARCHAR(128) NOT NULL COMMENT '全局事务ID',
    `context`       VARCHAR(128) NOT NULL COMMENT '序列化方式等上下文',
    `rollback_info` LONGBLOB     NOT NULL COMMENT '回滚信息（照片JSON）',
    `log_status`    INT          NOT NULL COMMENT '0:正常 1:已防御',
    `log_created`   DATETIME(6)  NOT NULL COMMENT '创建时间',
    `log_modified`  DATETIME(6)  NOT NULL COMMENT '修改时间',
    UNIQUE KEY `ux_undo_log` (`xid`, `branch_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT ='AT事务模式undo表';
```

### 2. rollback_info 里存什么（quantity 8→6 的照片）

```json
{
  "xid": "10.110.0.170:8091:123456789",
  "branchId": 641789253,
  "sqlUndoLogs": [
    {
      "sqlType": "UPDATE",
      "tableName": "stock",
      "beforeImage": { "rows": [ { "values": { "id": 1, "quantity": 8 } } ] },
      "afterImage":  { "rows": [ { "values": { "id": 1, "quantity": 6 } } ] }
    }
  ]
}
```

回滚 = 对比 before/after 生成反向 SQL：`UPDATE stock SET quantity = 8 WHERE id = 1`。

### 3. 注解怎么变成事务（GlobalTransactionalInterceptor 精简）

```java
public Object invoke(MethodInvocation methodInvocation) throws Throwable {
    GlobalTransactional anno = ...getAnnotation(GlobalTransactional.class);
    if (anno != null) {
        // 走"全局事务模板"：开事务 → 执行业务 → 提交/回滚
        return transactionalTemplate.execute(new TransactionalExecutor() {
            public Object execute() throws Throwable {
                return methodInvocation.proceed();   // 业务方法本体
            }
        });
    }
    return methodInvocation.proceed();
}
```

### 4. 普通 JDBC 提交怎么被"截胡"（ConnectionProxy）

```java
public void commit() throws SQLException {
    if (context.inGlobalTransaction()) {   // 这连接在全局事务里吗？
        processGlobalTransactionCommit();  // 是 → 注册分支 + 准备undo_log + 上报TC
    } else {
        targetConnection.commit();         // 不是 → 普通本地提交，无感知
    }
}
```

**AT 侵入小的根源**：业务代码一行不改，Seata 靠"数据源代理 + 注解拦截"两层偷换。

## 八、XID 是怎么跨服务传递的？

- SCA Seata 集成内置 **Feign 拦截器**（`RequestInterceptor`），请求发出前把当前 XID 写进 HTTP header（key: `tx_xid`）
- 接收服务拦截器再取出放进自己的 ThreadLocal
- **全程零业务代码**——这也是为什么 Seata 要求调用链必须在**同一个线程**里（Feign 同步阻塞天然满足）

## 九、部署决策（踩过的坑：版本兼容）

### 1. Seata Server 1.8.0.2 接 Nacos 注册 → 501 失败（已解决）

**事实**：Seata Server 1.8.0.2 内置 nacos-client **1.4.2**，只走旧版 **HTTP v1 API**；
Nacos Server 3.2.1 **已移除这些接口**。实测配 Nacos 注册，Seata 启动直接 **501**。
**当时方案**：改 file 注册（grouplist=10.110.0.170:8091 直连）。file 模式下 Nacos 控制台看不到
seata-server 属**正常现象**（客户端不经过 Nacos 做服务发现），事务功能完整。

### 2. 升级到 Seata 2.7.0 + 切回 Nacos 注册（当前状态 ✅）

- 服务端升级 **2.7.0**（Docker，`apache/seata-server:2.7.0`）
- **2.x 内置 nacos-client 2.x，兼容 Nacos 3.x**，501 根因消除
- Nacos 控制台（10.110.0.170:18080）服务列表可见 `seata-server`（分组 cloud-demo、集群 default、健康实例 1）
- 客户端由 SCA BOM 管理为 **2.1.0**（`org.apache.seata:seata-spring-boot-starter`），
  `mvn dependency:tree` 已验证

> ⚠️ **跨小版本**：服务端 2.7.0 vs 客户端 2.1.0，2.x 协议内部兼容一般能握手。
> 若验证回滚出现奇怪报错，第一排查方向就是版本差（可在 pom 显式覆盖客户端版本对齐 2.7.0）。

### 3. 客户端三层寻址（file 和 Nacos 注册都适用）

```
tx-service-group = my_tx_group      ← ① 我叫什么会员体系
vgroupMapping.my_tx_group = default ← ② 这个体系 → 对应集群名
                                     ↓
Nacos 里注册的 seata-server + 集群 default ← ③ 按①②找到 TC
```

报 `can not get cluster name` 多半是 ② 的映射 key 写错。

### 阶段 A 配置（三个服务 application.yml 各加一段）

```yaml
seata:
  application-id: ${spring.application.name}   # 业务服务身份（连 TC 时报备）
  tx-service-group: my_tx_group                # 事务分组：客户端"会员体系"名
  service:
    vgroup-mapping:
      my_tx_group: default                     # 会员体系 → Nacos 里的集群名
  registry:
    type: nacos                                # 指路：去 Nacos 找 TC
    nacos:
      server-addr: ${NACOS_ADDR:10.110.0.170:8848}
      username: nacos
      password: nacos
      group: cloud-demo                        # 和 seata-server 注册的 Nacos 分组一致！
      cluster: default
  config:
    type: file                                 # 自身配置走本地，避免"鸡生蛋"（连TC的配置还要先拉配置中心）
```

**为什么 registry 和 config 分开选**：registry=nacos 是"指路"（找 TC 在哪）；
config=file 是"自身配置放本地"。config 若也选 nacos，需要在 Nacos 发布几十个 Seata 配置 key，
发布漏了服务起不来，排查痛苦。先 file 跑通再考虑升级。

```
→ {"code":0,"data":2089912920705118209}   ✅ 库存 8 → 7
```

### ⑥ 进阶验证：undo_log 为什么"看不到记录"？（账本生命周期）

**问题**：回滚成功后查 undo_log 是 0 条，为什么？

**答案**：undo_log 是"进行中事务的临时账本"，不是"历史回滚记录表"。事务结束（无论提交还是回滚）账本就清空。

**实证**（临时把下单方法改成"落单成功后 sleep 20 秒再抛异常"，抓回滚前窗口）：

```
下单后 3 秒（sleep 窗口内，未回滚）：
  库存 7→5（扣库存成功）     stock_undo=1   order_undo=1   ← 账本有记录！
  rollback_info 里存着照片：
    {"sqlType":"UPDATE","tableName":"stock",
     "beforeImage":{quantity:7}, "afterImage":{quantity:5}}

sleep 结束（回滚完成）：
  库存 5→7（自动回滚）       stock_undo=0   order_undo=0   ← 账本清空！
  日志：Branch Rollbacked result: PhaseTwo_Rollbacked
```

**生命周期**：写照片（扣库存/落单时）→ 账本躺着（事务进行中）→ 提交（删账本）或回滚（读照片→反向SQL→删账本）。

> 踩坑：临时改代码模拟"落单后失败"时，`save()` 后面直接 `throw` 会被编译器判为
> **Unreachable code（死代码）**，编译静默失败、跑的是旧 class。要用 `if(true){ throw ... }` 包裹。

## 十三、踩坑记录

1. **SCA 2023.0.3.2 BOM 管的客户端是 2.1.0**：`mvn dependency:tree` 确认
   `org.apache.seata:seata-spring-boot-starter:2.1.0`。服务端若用 1.8.x 会不兼容，
   必须升到 2.x（2.7.0）——1.x 内置 nacos-client 1.4.2 走旧 API 连不上 Nacos 3.2.1（501）。

2. **undo_log 表不能靠 schema.sql 自动建（鸡生蛋）**：Seata 的 `DataSourceProxy` 在
   Spring 初始化数据源时就要校验 undo_log 表，而 `spring.sql.init`（schema.sql）是
   **数据源就绪之后**才执行的——顺序上表建不出来，服务直接报
   `in AT mode, undo_log table not exist`。解法：**手动连 MySQL 建表**（或 DBA 预建）。

3. **三个服务必须用同一个 `tx-service-group`**（`my_tx_group`），且 `vgroup-mapping`
   映射到 Nacos 里的集群名 `default`；registry 的 group 要和 seata-server 注册的
   Nacos 分组一致（本项目 `cloud-demo`），否则找不到 TC。

4. **服务端/客户端跨小版本**（2.7.0 / 2.1.0）实测可握手、可回滚，2.x 协议内兼容。

## 十四、思考题

1. 手动补偿三大缺陷（崩溃/补偿失败/时机误判）里，哪个是 Seata 也补不上的？（提示：全局事务超时）
2. AT 模式回滚靠 undo_log 照片，那"补偿插入的数据"怎么回滚？（提示：insert 的反向是 delete）
3. 为什么 Seata 要求调用链在同一个线程？异步线程池里 XID 会怎样？（提示：ThreadLocal）
4. 网关作为唯一入口，如果它挂了，正在进行的全局事务会怎样？（提示：TC 心跳超时）
5. Seata 的 TC 要 7×24 常开，它自己挂了怎么办？（提示：HA + 存储后端）
