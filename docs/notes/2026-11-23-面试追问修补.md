# 面试追问修补：幂等 / 缓存一致性 / 身份头伪造 / JWT 密钥 / 熔断降级 / Seata 热点行

> 背景：按"面试官顺着代码追问"反推，补上现有代码里一问就倒的漏洞。
> 每一节的格式都是：面试官怎么问 → 原来的问题 → 改了什么 → 怎么答。

---

## 1. 下单幂等

**面试官**：用户连点两次，或者网络超时前端重发，会不会生成两单、扣两次库存？

**原来**：`/api/order/create` 每次请求都完整执行"查商品 → 扣库存 → 落单"，没有去重。

**改动**：
- 前端每个"下单意图"生成一个 `requestId`（`frontend/src/api/order.ts` 的 `newRequestId()`），改了商品/数量或下单成功后换新的。
- `orders` 表加 `request_id` 列 + 唯一索引 `uk_request_id`。
- `OrderServiceImpl.create`（事务外）做两道防线，真正的全局事务拆到 `OrderCreateTx.execute`：
  1. **先查**：`request_id` 已存在 → 直接返回已有订单 ID，不再扣库存；
  2. **唯一索引兜底**：并发的重复请求都查到"没有"、都进了事务 → 只有一个能插入成功，另一个撞键 → Seata 全局回滚把它扣的库存加回 → 捕获异常后返回先到的那一单。

**怎么答**：
- 幂等 = 多次调用和一次调用效果相同，重复请求返回**同一个结果**（同一个订单号），而不是报错。
- 只靠"先查"不行：查和插之间有时间窗（check-then-act 竞态）。只靠唯一索引也不好：每个重复请求都要走一遍"扣库存 → 回滚"，白占库存行锁和 Seata 全局锁。
- **已知边界**：两个重复请求真正并发时，后到的那个在扣库存时要等先到的全局事务释放库存行的全局锁。等待超过 Seata 的锁重试上限时，后到的请求会返回"系统繁忙"，而不是第一单的订单号。即便如此也不会多下单；前端用同一个 `requestId` 再提交一次，拿到的就是第一单。
- 为什么拆出 `OrderCreateTx`：`@GlobalTransactional` 靠 AOP 代理，同类 `this.xxx()` 自调用会绕过代理，注解失效。
- 其他方案对比：**Token 机制**（先 `GET /token` 发令牌存 Redis，提交时 `DEL` 成功才处理）适合"表单防重提"；**唯一业务键**（本项目）最简单可靠，由数据库兜底；**分布式锁**只能防并发、防不了"先后到达"的重复。

## 2. 缓存里的库存是脏数据

**面试官**：下单后详情页的库存为什么没变？库存这种高频变化的数据该不该缓存？

**原来**（两个问题）：
1. 详情缓存把"商品 + 库存快照"一起存了，只有商品服务自己的 `/buy` 会删缓存；走 `service-order` 下单时扣的库存，商品服务感知不到，缓存里的库存就一直是旧的，最长 10 分钟。
2. **缓存根本不命中**：`GenericJackson2JsonRedisSerializer(objectMapper)` 传入了 Spring 的 ObjectMapper，这个构造器不会写 `@class` 类型信息，读回来是 `LinkedHashMap`，`instanceof ProductDetailCacheDTO` 永远是 false，所以缓存只写不读。（已用代码复现：写入的 JSON 里没有 `@class`，读出来的类型是 `LinkedHashMap`。）

**改动**：
- 新增 `ProductInfoCache`：只缓存商品基础信息，**库存每次实时 Feign 查**（动静分离）。
- 改用 `StringRedisTemplate`，读的时候用 `objectMapper.readValue(json, Product.class)` 显式指定类型。
- Key 从 `cloud-demo:product:detail:{id}` 改成 `cloud-demo:product:info:{id}`，旧格式的数据会自然过期。
- Redis 出任何异常都当作未命中，回源 DB，不影响主流程；数据损坏时删掉这个 key 再回源。
- 删除商品：先删 DB，再删缓存（Cache Aside 的写策略）。

**怎么答**：
- 变化频率高、强一致要求高的数据（库存、余额）不适合放进普通的 Cache Aside 缓存。要么实时查，要么在秒杀场景下让 Redis 成为库存的"主"（Lua 原子预扣 + 异步落库），这是另一套设计，不是"缓存"。
- 为什么是"先更新 DB 再删缓存"而不是"先删缓存"：先删缓存的话，在"删缓存"和"写 DB"之间来一个读请求，会把旧值回填进缓存，脏数据要等 TTL 过期。先更新 DB 也有很小的并发窗口（读请求在写之前读到了旧值、在删缓存之后才回填），可以用延迟双删或订阅 binlog 删缓存来补，TTL 是最后的兜底。
- 不用 default typing（`@class`）的另一个理由：Jackson 多态反序列化历史上出过多次反序列化漏洞。

## 3. 身份头可伪造

**面试官**：我自己在请求里带上 `X-User-Roles: ADMIN` 会怎样？绕过网关直连服务呢？

**原来**：网关只在验签成功后**设置** `X-User-Id`/`X-User-Roles`；白名单路径会把客户端带来的这两个头原样透传。下游 `AdminInterceptor` 无条件信任这两个头。

**改动**（`AuthGlobalFilter`）：
- 第一步无条件删除客户端带来的 `X-User-Id` / `X-User-Roles`，白名单路径同样会删；之后只有验签成功才由网关写入。
- 兼容 `Authorization: Bearer xxx`（RFC 6750 写法）和不带前缀的裸 token。

**怎么答**：
- 原则：身份信息只能由信任边界（网关）产生，**客户端传来的同名头必须先清洗**。
- 网关清洗只能防住"经过网关"的伪造。业务服务端口（8081~8084）如果能被直连，伪造照样有效。生产上的做法：
  1. 网络隔离：业务服务只监听内网或在 K8s 里只暴露 ClusterIP，只有网关对外；
  2. 再加一层（零信任）：网关给下游签一个内部 token（或 mTLS），下游验签而不是只看明文头。

## 4. JWT 密钥写死在代码里

**面试官**：密钥怎么管理？怎么轮换？为什么不用 RS256？token 怎么注销？

**原来**：`SECRET = "1234...9012"` 写死在两个 `JwtUtil` 里，跟着代码进了 git。

**改动**：
- 网关和用户服务都改成从 `jwt.secret` 读取，本地 yml 里写成 `${JWT_SECRET:}`，值来自**环境变量 `JWT_SECRET`** 或 **Nacos 配置**（不同步到 `docs/nacos-config`，那里会进 git）。
- 启动时校验：没配置或不足 32 字节，直接启动失败（fail fast）。
- `JwtUtil` 从静态工具类改为 Spring Bean，过期时间可配置（`jwt.expire: 2h`）。

**怎么答**：
- **HS256 vs RS256**：HS256 是对称签名，能验签的一方也能签发，网关一旦泄露密钥，攻击者就能伪造任意 token。RS256 由用户服务持有私钥负责签发，网关只拿公钥验签，公钥泄露也伪造不了。服务多了以后，还可以通过 JWKS 接口分发公钥。
- **轮换**：token 头里带 `kid`，验签方同时认新旧两把 key，过渡期等于 token 的最长有效期，过渡期结束后下线旧 key。
- **注销/踢人**：JWT 无状态，签发后服务端收不回来。常见做法是短 access token（15 分钟到 2 小时）+ refresh token，注销时把 token 的 `jti` 放进 Redis 黑名单，TTL 设为 token 的剩余有效期。这其实是用一点状态换回控制权。

## 5. Feign 没有超时、熔断、降级

**面试官**：库存服务变慢时订单服务会怎样？会不会雪崩？重试和幂等是什么关系？

**原来**：没有配置 Feign 超时，用的是默认的 connect 10s / read 60s。库存服务一慢，订单服务的 Tomcat 线程就全卡在等待上，最后订单服务也挂掉，这就是雪崩。也没有熔断和 fallback。

**改动**：
- **超时**：Nacos `service-order.yaml` / `service-product.yaml` 配置 connect 1s / read 2s。本地开启 `spring.cloud.openfeign.client.refresh-enabled`，超时在 Nacos 发布后热更新。
- **降级**：`service-order`、`service-product` 引入 Sentinel，`feign.sentinel.enabled=true`，每个 `@FeignClient` 都配了 `fallbackFactory`。下游超时、宕机或熔断时，返回 `70002 依赖服务暂不可用（原因）`。
- **熔断**：Sentinel 熔断规则从 Nacos 拉取（`service-order-degrade.json` / `service-product-degrade.json`），包含异常比例 ≥ 50% 和慢调用（> 1s）比例 ≥ 50% 两条，统计窗口 10s、最少 5 个请求，熔断 10s。
- **不重试**：OpenFeign 默认 `Retryer.NEVER_RETRY`，classpath 上也没有 spring-retry，LoadBalancer 不会重试。

**测试覆盖**（`StockFeignClientWiringTest`，用 JDK HttpServer 模拟库存服务）：
- 库存服务卡 1.5s → 500ms 超时后走 fallback，并且只请求了一次（没有重试）；
- 连续 500 错误 → 熔断打开 → 之后的请求**根本不发出去**，直接返回"熔断中"。

**怎么答**：
- 超时、熔断、降级的分工：**超时**限制单次调用最多等多久；**熔断**在下游已经不健康时，连请求都不发，快速失败，给下游留出恢复时间；**降级**决定失败时返回什么。
- 下单场景的降级只能返回"失败"，不能编造"扣减成功"。fallback 返回失败后下单方抛异常，触发 Seata 全局回滚。
- **超时 ≠ 失败**：读超时时库存服务可能已经扣成功了。本项目有 Seata 兜底：库存分支已经注册在 XID 下，全局回滚时 TC 会把它回滚；如果分支在全局回滚开始之后才来注册，注册会失败，本地事务随之回滚。没有 Seata 时，就要靠"扣库存接口本身幂等（按订单号去重）+ 对账"。
- **重试的前提是幂等**：扣库存不是幂等操作，开了重试就可能扣两次。如果确实要重试，先让下游按业务唯一键去重。
- 超时值怎么定：大于下游正常 P99（可以看 Grafana），小于上游（网关/前端）的超时，否则上游已经放弃了，下游还在白干。

## 6. Seata AT 用在扣库存热点行上（只讨论，没有改代码）

**面试官**：并发高时全局锁冲突怎么办？秒杀能不能用 AT？

**要点**：
- AT 一阶段**本地事务直接提交**，但这一行的**全局锁**要等二阶段结束才释放。热点商品的库存行上，同一时刻只有一个全局事务能持有锁，其他事务排队重试（`lock retry`），吞吐量被锁住的时长卡死。
- 所以 AT 适合**并发不高、追求开发效率**的业务。秒杀或热点库存不能用 AT：
  - **Redis 预扣库存**（Lua 保证原子性）+ MQ 异步落单 + 最终一致（项目计划里的秒杀专题）；
  - 或者 **TCC**：Try 阶段冻结库存（`frozen` 字段），Confirm/Cancel 阶段再处理。没有全局锁，但要自己处理空回滚、幂等、悬挂三个问题；
  - 或者**库存分桶**：把一行热点库存拆成 N 行，分散锁竞争。
- AT 的"读未提交"：一阶段已经本地提交，别的事务能读到"可能被回滚"的数据。需要隔离时用 `SELECT ... FOR UPDATE`（Seata 会去检查全局锁）。

4. **前端**：下单请求现在必须带 `requestId`，前端已经同步修改；其他调用方（Postman/curl）需要自己加上这个字段。
